## Answers

1. **Decoding.** Every file with a channel list decodes: 86 of 87 `.ld` files (81 distinct contents, 1.73 GB), 11,910 channels, no unknown `(dtype_a, dtype)` pair, no list cycle, no out-of-range sample array. The 87th file is a 4.9 KB converter test output whose header points `meta_ptr` and `data_ptr` at the end of the file (no channels). The public notes are enough to decode samples, but they miss several layout facts that a reader must handle (§3).
2. **Pass criteria (07 §11).** 100 % of channels decode. Integers are bit-exact and floats are bit-exact against the converter's output where it decodes the channel; 53,431 cells of five vendor-software CSV exports agree within print precision; three of those exports (6,720 cells) hold C125 logger data. Scaled integers differ from the converter by at most 2 F32 ulp, because the converter computes in single precision; the reference decoder rounds the exact value once. The 8 F64 channels have no oracle (the converter returns no samples for them).
3. **Shift vs mul: afterMul**, settled by physical evidence on logger data. Primary: `<user-logs>\20251009-1552000.ld` (logger type C185), channel `Gbox Oil Temp`; corroborating: `<user-logs>\20260420-0120200.ld` (C127, file as downloaded), channel `Ambient Air Temp` (§7). Default `beforeMul` (D-037) is contradicted. A vendor-software CSV export of either file is the remaining confirmation that 05 §3.6 asks for; none exists on the machine yet.

Notes on the classes:

- **Logger, as downloaded** (C125 serial 4714, C127, M1): the event block follows an opaque device-configuration region (≈1.4 MB on C125, ≈3 MB on M1). That region is not parsed and nothing from it is recorded beyond its extent.
- **Logger, header-modified copy** (`_Pro` files, `_Pro_bad`, one M1 `_03`): where the original is on disk, the copy is byte-identical except header bytes 0x046–0x055 and 0x5DE–0x5E1 (device serial/type/version, u16@0x054, u32@0x5DE), so samples are unaffected. The producer cannot be told from the header.
- **PC layout**: event block directly after the header, u16@0x040 = 2, u16@0x054 = 0x0080, channel "counter" = 20101 + index, often per-channel extension data. Either the logger identity is kept (8 files: C125, C185, M1, including the three M1 exports in the converter's reference folder) or the generic identity `MTCA2LD`/50196/100 is written (43 files). The user's converter writes the same generic header as the vendor's PC software (the T2 test models carry it too), so header evidence cannot separate converter output from vendor-software output; file names and folders suggest that most of the 39 non-sample files are converter output.
- **Sim exporters**: none. No file matches the gotzl or motec-i2 writer defaults, and no counter follows gotzl's 0x2EE1 + index.

## 5. Timing

Python 3.12 on the developer machine, warm file cache; informative only (AC-M0-12's 200 ms budget applies to the C++ reader on the 500 MB synthetic file).

- Probe (median of 5): median 0.38 ms over 81 distinct files, maximum 59 ms. The [i3rs] enum signature scan dominates the slow cases: without it the M1 logger files with a ≈3 MB configuration region drop from 43–59 ms to 2–6 ms and the 731-channel PC-layout file from 34 ms to 12 ms. The 282 MB file probes in 1.3 ms (57 channels).
- Full decode with exact statistics of every sample: 16.1 s for all 81 distinct files (1.73 GB); 3.5 s for the 282 MB file, 1.8 s for the 128 MB file.
- Converter parser for comparison: its metadata pass (`parse()`, with its own enum and gap heuristics) takes up to 0.31 s per file (the 282 MB file); sample extraction is numpy-backed and was not timed separately.

## 10. Deviations from the design documents

1. **Scaling default.** Evidence favours afterMul against D-037's `beforeMul` (§7). Not changed in any design document; recommended for D-037.
2. **05 §3.3 pointer width** u16 → u32 (D1).
3. **05 §3.4 / §3.8 record layout.** Fixed 124 or 212-byte strides do not hold (D2, D3); `m1-212` detection by stride and `sim-exporter` detection by counter (D8) do not work on real files.
4. **05 §3.4 `num_channs`** is two u16 (D5).
5. **05 §3.5** `dtype_a` 0x06 holds plain integers, not bitfields (D9).
6. **08 §12 day 4** expected a C++ `ld_probe.exe` and a `spike/s1-ld-reader` branch. M0 has no reader yet and git history must not change in this phase, so the spike is Python and its files are untracked in the working tree.
7. **Comparison script and numpy.** `python -I` hides the user site-packages; `compare_converter.py` appends that folder to `sys.path` explicitly so the converter's numpy import works, without letting anything there shadow the standard library.
8. **Independence (D-041) vs the user's request.** The user asked that reading be the inverse of the converter's writer. That applies to the `esses_formats` reader. `tools/ld_ref_decode.py` was written from the public notes before the converter was touched; the converter was then used only through its API (introspected, not read) and its outputs compared. An inverted-writer reader will be checked against this independent oracle and the vendor CSV exports, so a mistake shared by writer and reader still fails.
9. **Extra inputs.** `~\Documents\MoTeC\` was not in the task's list; it was included (10 `.ld`) because it holds the user's own logger downloads, and it adds M1 and C125 coverage.
