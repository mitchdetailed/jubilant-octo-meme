# M4 — Hardening and 0.1: milestone note

Status: **wave 1 contracts laid down** (branch `m4-hardening` from `main` 59df0f8, 2026-10-18; D-206). Nothing
of M4's behaviour is built yet: every new class and function is an `M4-STUB` (or final where the contract
needed it, §2) and the shell's M4 wiring is reached through one hook (§2.1). M4 runs as several workflows:
**wave 1** (this contract, then the packages budget, reload, hidpi and followups in parallel) and **wave 2**
(packaging, soak, the Saturday walkthrough with the CLI golden tests, and the user docs). Each package keeps
to its files (§3) and records what it built in its own subsection of §8. The milestone closes (07 §1.2)
when AC-M4-01..10 are met (§4), the maintainer's steps of §6 are done, and `v0.1.0` is tagged; 0.1 is
accepted when M4 exits (07 §2.5).

## 2. Contracts (2026-10-18, D-206)

### 2.1 The one shell hook

`MainWindow` creates one `ShellExtension` (`libs/widgets/include/esses/widgets/shell/shell_extension.hpp`) per
M4 package in a fixed order (budget, reload, hidpi, followups, about, docs; `src/shell/main_window_m4.cpp`) as
direct `QObject` children named `m4.<key>`, and calls their virtuals at fixed points: `buildWidgets(central)`
(end of `buildWidgets`), `registerCommands()` (after the M3 commands, before the planned rows),
`buildMenus()` (after the menus), `windowReady()` (end of the constructor), `worksheetActivated(i)` (after
the M3 followers; -1 before the worksheets are rebuilt, also before `windowReady`) and `teardown()` (first
thing in `~MainWindow`; the extensions are then deleted, before any widget, dock or model). An extension
reaches the window through `window()` (public accessors) and `impl()` (`MainWindow::Impl`; write
`auto& d = impl();`, the type is private), plus the window's `hint()` and `showEditor()`. Tests find one
with `shellExtension<T>(window)`. A status-bar field an extension adds to `impl().status` is found by
`MainWindow::statusField` and cleared on every worksheet switch, so it is set again in `worksheetActivated`.

### 2.4 Rules for the packages

As in M2 and M3: an `M4-STUB` is replaced in place and its marker removed; tests of a stub's behaviour belong
to its package and their expectations come from the design, never from the code under test (D-041); a
signature another package consumes changes only together with that consumer, through the coordinator; a
departure from the design is an ADR in `DECISIONS.md` Addendum A with the D-id the coordinator assigns (and
an index row) and a line in §9. Keymap: a package that implements a planned M4 row (`file.reload_source`,
`help.contents`) flips it to `implemented` in `data/keymaps/default.json` and adds its `KEYMAP_TEST` entry to
its own `tests/ui/keymap/keymap_m4_<package>_cases.hpp`; commands without a row (`help.about`,
`file.continue_open`, `file.cancel_open`) get none (06 §14.4 does not list them; D-203 (ah)). New pixel
goldens rendered locally are provisional (`"generatedOn": "windows"`, report mode) until the coordinator
replaces them from the ubuntu artefact; `DrawList` JSON goldens are exact everywhere. Shared documents
(`CHANGELOG.md` under "Unreleased (M4)", `DECISIONS.md`, `ARCHITECTURE_OUTLINE.md` names, `CLEANROOM.md`, the
library `README.md`s, this note) take small append-only edits after re-reading the current text, each in the
package's own entry or subsection.

### 6.2 SMB case (AC-M4-10)

build of this branch. The offscreen half on a local disk is `ui.tst_reload_source` (and the NTFS half of 02 §8

   least one rename-over writer replaces the file while the view keeps the old bytes). Record the three `SMB: ...`
