# Esses design set

**Esses** (working codename) is a clean-slate, free and open-source reimplementation of the MoTeC i2 Pro analysis workflow: a Qt 6 Widgets application over a Qt-free C++20 core, Windows first, built by one developer with AI assistance. Release 0.1 aims to let a circuit race engineer replace i2 Pro for a Saturday. That means opening `.ld`/`.ldx` and CSV logs, selecting Main and overlay laps, comparing cursor-linked time/distance graphs with variance and offsets, running existing i2 maths expressions unchanged, and using reports, histograms, scatter plots and track maps in a project folder that autosaves and reopens where it left off. The analysis application comes first. Import of i2 workbooks, workspaces and schemes, broad format support, the plugin SDK, scripting and video follow at v1.0 and v1.1. Nothing in the product uses MoTeC code, assets or trademarks.

## The twelve decisions that shape everything

1. **D-001** Synthesis base: parity-first's product specification (i2 behaviour as the contract) on a layered core, with grafts from the other three proposals.
2. **D-002** Licence: MIT for the whole tree, DCO, no CLA, no relicensing; Qt modules are LGPLv3 and dynamically linked (confirmed 2026-10-10).
3. **D-003 / D-125** Codename Esses; "MoTeC" and "i2" never appear in identifiers, file names or UI strings except through a five-class nominative allow-list enforced by CI (name confirmed 2026-10-10; no trademark search scheduled, the name may change later by scripted rename).
4. **D-004 / D-005 / D-038 / D-128** Clean room: no disassembly or decompilation. i2 behaviour comes only from help pages, shipped files, public sources and, since the user's 2026-10-10 permission (Q-03), black-box observation on the user's licensed install. i2 runs only on MoTeC-device data, never on Esses output. AI prompts never contain vendor text, and every derived behaviour has a `CLEANROOM.md` line.
5. **D-007 / D-031 / D-123** Qt-free line: data, formats, maths, analysis, documents and plot geometry build without Qt. One priority `TaskPool`, and the GUI thread never blocks. No worker waits on queued work (Rule W), and one `Dispatcher` bridges workers to the GUI.
6. **D-008 / D-009 / D-129** Time is `int64` microseconds and rates are exact rationals with an exact inverse `indexAt`. Series are uniform or timestamped, F32 by default, with per-chunk validity.
7. **D-011 / D-012 / D-043** Column store of 65,536-sample immutable chunks with a factor-4 min/max pyramid, pinned by `ChunkHandle`. Decimation is exact M4. LRU eviction arrives in M5.
8. **D-013 / D-014 / D-015** The channel name is the identity, resolved through Mappings → Aliases → name with a trace. Laps are always derived from markers by declarative rules. User edits live in a sidecar beside the log; the `.ldx` is merged and never written in place.
9. **D-016 / D-134** Distance mode runs on a built-in corrected speed/distance module. Each lap has a `DistanceIndex` and laps chain across the outing. F9 preserves the zoom.
10. **D-020 / D-021 / D-022 / D-139** Maths is 100 % i2-source-compatible; dimension mismatches are warnings, never rejections. Nodes are version-keyed and cached like logged data. In 0.1 each node is evaluated whole-extent, in parallel across nodes.
11. **D-025 / D-137** Plot engine: a QPainter raster backend behind a Qt-free `DrawList` IR. Only the Static layer is a cached image. A GL backend is built only if a measured budget fails on the reference machine (D-042).
12. **D-035 / D-045 / D-046** MVP 0.1 is the circuit workflow without i2 file importers (those are the first v1.0 item). The plan is ≈ 42 calendar weeks to 0.1, with tests at 30 % and 15 % contingency; the user accepted the scope cut and the plan on 2026-10-10 (Q-05). An optional cut list is available (user must confirm).

## How these documents were produced

1. **Research (Phase 1).** The i2 Pro help pages, the XML configuration and template files shipped with i2, the SDK samples, public release notes and the open-source projects in this space were read. The result is a 271-feature inventory, a concept model, a configuration model, a formats survey, a landscape of existing tools and a technology-stack assessment (`background/research/`).
2. **Architecture panel.** Four architects each wrote an independent proposal with a different bias: core-first, parity-first, performance-first and ecosystem-first. Three judges scored all four through different lenses: a solo developer with limited time, an i2 power user, and a systems architect (`background/design-panel/`). Parity-first won the weighted tally narrowly.
3. **Synthesis.** `DECISIONS.md` (ADRs D-001–D-036) resolves every contradiction the judges listed, and `ARCHITECTURE_OUTLINE.md` fixes the names, interfaces, schemas, MVP scope and milestones that bind the writers.
4. **Section writers.** Seven writers expanded the outline into documents 00–08 and recorded the gaps they found.
5. **Critics and revisers.** Four critics reviewed the whole set and reported cross-document conflicts, gaps and feasibility problems. Revisers applied the fixes, and the decisions this process proposed became Addendum A (D-037–D-141). A final editorial pass applied the remaining cross-references, collected the open questions and wrote this page.

**Clean-room rule.** The design and the future code are written from public information only: the help pages as displayed by the shipped help viewer, configuration and template files shipped with i2, SDK sample sources read for interface shape, public release notes and permissively licensed public projects. GPL projects were read for understanding only. No MoTeC binary was disassembled or decompiled, and no MoTeC code, help text, icons, templates or sample files are copied into the product. Files the user's own i2 install wrote were consulted during research on 2026-10-09; on 2026-10-10 the user confirmed that this use stands (Q-03, D-039). The user also permitted i2 CSV/report exports of their MoTeC-device logs as private test oracles and black-box observation of i2 on their own install; observation never includes disassembly, and the legal check that it is not "reverse engineering" under the EULA is the user's own responsibility. `CLEANROOM.md` in the product repository will name the source of every format fact and every i2-derived behaviour.
